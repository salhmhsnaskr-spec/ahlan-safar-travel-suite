# خطة الاختبار التكاملي المستقل للحذف الدائم — أهلاً سفر

## الهدف وحدود الموافقة

اختبار الإصلاحات الحالية على منصة مستقلة كاملة للمصادقة وقاعدة البيانات والتخزين، بجلسات حقيقية واتصالات متزامنة، دون إعادة بناء نظام الحذف أو إعادة مجموعة الاختبارات السابقة.

**هذه خطة فقط.** اعتمادها لا يسمح بالاتصال بالإنتاج أو إنشاء موارد مدفوعة أو نشر التطبيق أو رفعه إلى GitHub. قبل أي إعداد خارجي يُحدد الجهاز/المشغّل والكلفة ونطاق الحسابات، وتُطلب موافقة صريحة. إذا لم تتوفر بيئة مستقلة مجانية موثقة، نتوقف بتقرير العائق.

## 1. البيئة الأقل تغييرًا والأكثر أمانًا

استخدام جهاز موجود يدعم Docker لتشغيل Supabase محلي مستقل، مع PostgreSQL 17 وAuth وStorage وصندوق بريد تأكيد محلي. هذا يتوافق مع حواجز العناوين المحلية الحالية؛ مشروع مستضاف مستقل لا يعمل معها دون تغيير منفصل غير مشمول بالخطة.

المتطلبات:
- جهاز/مشغّل موجود وموافق عليه، Docker عامل، مساحة وذاكرة كافيتان تُفحصان قبل التشغيل، ونسخ الأدوات مثبتة ومتوافقة.
- نسخة مستقلة من مصدر التطبيق الحالي، واعتمادياته، دون `.env` أو جلسات أو أسرار الإنتاج؛ لا تعديل لملفات التكامل المولدة في المشروع الأصلي.
- تكوين مستقل مصرح به لجميع عناوين التطبيق والمصادقة والتخزين، ومفتاح نشر محلي ومفتاح خدمة محلي جديدان فقط. متطلبات التشغيل الدقيقة تُتحقق قبل تجهيز النسخة.
- قاعدة وملفات تخزين دائمة خلال سيناريوهات توقف العامل، ثم قابلة للمحو الكامل بعد الاختبار.
- تنفيذ العامل بهوية نظام غير root، في عملية منفصلة عن المتصفح؛ لا تفعيل وحدة الخدمة الحالية التي تفتقر إلى `User=` كما هي.
- إن اختير GitHub Actions لاحقًا: تشغيل يدوي فقط، لا رفع أو إنشاء workflow الآن، مع دليل الحد المجاني ومنع التجاوز المدفوع قبل التشغيل. عدم إثبات ذلك يوقف التنفيذ.

### بوابة العزل قبل أي عملية

التحقق من أن كل عنوان اتصال محلي ومخصص للنسخة المستقلة، وأن جميع الجلسات جديدة، وعدم وجود قيم إنتاج في التكوين. حظر خروج عمليات التطبيق والعامل والمتصفحات خارج النطاق المسموح؛ تنزيل الحزم/الصور في مرحلة إعداد منفصلة لا تحمل أسرارًا. إيقاف فوري لأي محاولة اتصال خارج النطاق.

لا نقرأ الإنتاج لإثبات عدم تغييره: الدليل هو غياب بيانات اعتماده، وحاجز الشبكة، وسجل وجهات الاتصالات للبيئة المستقلة فقط.

## 2. إعادة البناء باستخدام الملفات الحالية

1. تشغيل المنصة المستقلة والتحقق من صحة Auth وStorage والبريد المحلي قبل الاختبار.
2. تطبيق ملفات SQL المرجعية الستة بالترتيب ومطابقة بصماتها؛ لا إعادة استخراج الإنتاج ولا استخدام ملف dependency shells الخاص بـPGlite.
3. تطبيق المعالجات المحلية `00700 → 00800 → 00900 → 01000 → 01100` بالترتيب. يشمل هذا التشغيل `00800` لاختبار توافق القيود مع الإنهاء الصريح.
4. إنشاء حاوية `documents` الخاصة من إعداد البيئة/API التخزين، لا كتابة سجلات الحاوية مباشرة عبر SQL.
5. فحص GRANT وRLS وPUBLIC والمنح الافتراضية والأدوار الموروثة. إذا أوقف `01100` الإعداد بسبب عضويات منصة أو مالك افتراضي إضافي، نراجع السبب ونعرض التعديل المطلوب؛ لا تجاوز للحارس أو إزالة أدوار مُدارة عشوائيًا.
6. تشغيل نسخة التطبيق والعامل المحلي بمهلات وتجديد الحجز الحاليين، مع مراقبة الاختبار. لا تنفيذ تصميم عامل الإنتاج أو تفعيل جدولة مستضافة.

## 3. أربع هويات حقيقية ومكتبان

لا تُنشأ الآن حسابات. بعد الموافقة، التسجيل الرسمي والتأكيد عبر صندوق البريد المحلي، دون تعديل `auth.uid()` أو صنع JWT أو تعطيل تأكيد البريد.

| الهوية | الدور في الاختبار |
|---|---|
| A | مدير نشط للمكتب الأول والثاني؛ الحساب المشترك المراد إثبات بقائه. |
| B | موظف نشط بالمكتب الأول؛ اختبارات الرفض والوثائق الخاصة. |
| C | مدير نشط بالمكتب الثاني فقط؛ مستخدم خارج المكتب الأول، وحالات آخر مدير منفصلة. |
| D | مالك منصة، دون عضوية بالمكتب الأول؛ حذف المكتب ورفض حذف العميل دون توسيع الصلاحية. |

كل هوية لها سياق متصفح منفصل وجلسة رسمية مستقلة. إنشاء المكاتب عبر التطبيق وقبول العضويات عبر الدعوات. تعيين D في `platform_owners` بإعداد اختبار مصرح به في القاعدة المستقلة فقط، لا بيانات المستخدم القابلة للتعديل.

نستخدم عملاء وطلبات وحجوزات ومهام ووثائق ومشاركات ورحلات وخدمات خاصة وسجلات نشاط تجريبية مرتبطة بمعرّف تشغيل واحد. نضيف ملفًا معلومًا دون بيانات وثيقة تحت بادئة المكتب لاختبار تنظيف المكتب، ولا ننسبه إلى عميل بالتخمين. تجهيز السيناريوهات اللاحقة يستخدم مكاتب مؤقتة جديدة مع الهويات الأربع نفسها، لا حسابات إضافية.

## 4. سيناريوهات الاختبار وأدلة القبول

| المجال | السيناريوهات | معيار القبول |
|---|---|---|
| الجلسات والصلاحيات | A يحذف العميل؛ B يرفض حتى لعميل بلا توابع وعبر RPC مباشرة؛ D دون عضوية يرفض العميل ويُسمح له بحذف المكتب؛ C يرفض الوصول للمكتب الأول؛ جلسة غائبة/غير صالحة؛ إيقاف B ثم إعادة التحقق بالجلسة القديمة. | النجاح فقط للأدوار المحددة؛ الرفض لا ينشئ مهمة ولا يحذف ملفًا أو سجلًا. لا تكفي الواجهة دليلًا. |
| العضويات | رفض INSERT/UPDATE/DELETE المباشر بما فيه role وstatus والهوية؛ تغيير الدور عبر RPC للمدير؛ رفض الموظف؛ تخفيض/إيقاف/إزالة آخر مدير، ومحاولتان متزامنتان ضد مديرين. | تبقى هوية العضوية وتاريخها؛ يوجد مدير نشط واحد على الأقل دائمًا؛ الرفض لا يترك تغييرًا جزئيًا. |
| الوثائق | حذف سجل مباشرة والملف موجود؛ حذف مصرح به عبر التطبيق؛ وثيقة الموظف الخاصة مقابل وثيقة غيره؛ تكرار حذف بعد فقد استجابة. | السجل لا يُحذف مستقلًا؛ الاكتمال بعد غياب الملف وتصفية السجل فقط؛ نطاق المكتب الآخر سليم. |
| غياب Storage | رفع/قراءة الملف ثم حذفه؛ HEAD يرجع 404؛ الملف المفقود مسبقًا؛ مقارنة مع 401/403/500 وانقطاع الشبكة والمهلة. | 404 المؤكد غياب؛ أخطاء أخرى لا تُعتبر نجاحًا. الملفات الحقيقية عبر API؛ حالات الخطأ المصطنعة تُوسم حقن أعطال لا استجابة مزود حقيقية. |
| حذف العميل | توابع مباشرة وغير مباشرة، وثائق عبر طلب/حجز، مشاركة في رحلة مشتركة، وأحداث التدقيق المرتبطة. | لا سجلات أو ملفات ضمن النطاق المعروف؛ تبقى الرحلة والعميل الآخر والخدمات المشتركة. بيانات تاريخية مجهولة الارتباط تُذكر كحد غير مثبت. |
| حذف المكتب والبيانات المشتركة | حذف بمدير ثم بمالك في سيناريو منفصل؛ ملف بادئة بلا سجل؛ حساب A مشترك؛ بيانات وملفات المكتب الثاني. | حذف جميع السجلات المملوكة للمكتب وملفات `documents` ببادئته؛ بقاء حساب A وملفه وعضويته ودخوله وعملياته بالمكتب الثاني؛ تطابق بصمات بيانات وملفات المكتب الثاني قبل/بعد. |
| الحجر والحماية | قراءة/كتابة مباشرة أثناء الانتظار، رفع/تعديل Storage، استدعاء `deletion_frozen` من C، تقارير وقراءة روابط موقعة قديمة. | رفض النطاق غير المصرح وعدم قفل المكتب الآخر؛ منع نشاط البيانات المحجورة حسب السياسات. الروابط القديمة تُقاس حتى انتهاء صلاحيتها ولا يُدعى إبطال النسخ المنزلة. استثناء invitation_preview المعروف يُوثق، لا يُخفى. |
| الأعطال والتعافي | فشل بعد دفعة ملفات، فشل الإنهاء، فقد الاستجابة بعد نجاح الإنهاء، فشل حفظ حالة الفشل، إيقاف العامل بعد claim وبعد إزالة ملف، ثم إعادة تشغيله. | مهمة دائمة قابلة للاستئناف؛ لا نجاح زائف؛ إنهاء ذري؛ إعادة التشغيل يسترد الحجز المنتهي ويكمل دون تدخل لإعادة إنشاء المهمة. |
| المهام الطويلة | ملفات تتجاوز 100 و500 لاختبار الدفعات والصفحات؛ تنفيذ يمتد أكثر من خمس دقائق، تعطل renewal، منفذ قديم بعد استرداد الحجز. | التجديد يبقي المحاولة السارية؛ فقد الحجز يوقف عمل المنفذ القديم؛ الإنهاء القديم مرفوض؛ لا ملفات أو صفوف مفقودة من التعداد. |
| التزامن الحقيقي | طلبي حذف للهدف نفسه؛ هدفان بالمكتب نفسه؛ عاملان؛ تحديث يحجز صفًا مقابل بدء/إنهاء الحذف؛ رفع جارٍ وقت إنشاء المهمة. | اتصالان مستقلان متداخلان بدليل توقيت/حواجز؛ مهمة نشطة واحدة للمكتب؛ لا انتظار دائري مستمر؛ 55P03/40P01 يرجع بأمان ويُعاد؛ لا ملف متأخر يتيم ولا كتابة تتجاوز التجميد. |
| الأسرار والصلاحيات | فحص المتصفح والطلبات والملفات المولدة؛ ACL فعلي للأدوار وPUBLIC والمنح الافتراضية. | لا مفتاح خدمة في العميل أو التقرير؛ لا TRUNCATE غير لازم للعملاء أو وصول موروث غير معتمد؛ لا سلطة إنهاء/نطاق للمستخدم العادي. |

## 5. التشغيل والقياس

تشغيل حزمة تكامل حرجة واحدة بعد نجاح بوابات البيئة. لا تشغيل الاختبارات الـ92 أو فحص عميق أو تصدير التقارير أو بريد خارجي. لا تكرار سيناريو ناجح إلا إذا تغير ما يمسه إصلاح لاحق، مع توثيق السبب.

الأدلة: حالة UI للمستخدم الحقيقي، نتائج RPC/API كما يراها دوره، استعلامات تحقق مستقلة بصلاحية مراقبة محلية، فهرس التخزين وفحص غياب الملف الفعلي، بصمات سجلات وملفات المكتب الثاني، أرقام المحاولات والتجديد، توقيت الاتصالات والأقفال، وسجل توقف/إعادة تشغيل العامل. الأدلة تُنقح من الأسرار وبيانات الجلسات.

مراقبة العامل في الاختبار تقيس عمر الانتظار والتقدم والمحاولات والحجوزات المنتهية وآخر مرور ناجح. هذه مراقبة لحزمة الاختبار، وليست تنفيذًا لمراقبة عامل الإنتاج.

## 6. معايير الحكم النهائي والتنظيف

**قبول الاختبار المستقل:** نجاح جميع السيناريوهات الحرجة، عدم وجود ملفات/سجلات يتيمة ضمن النطاق المعلوم، عدم تغيير المكتب الآخر، رفض كل المسارات غير المصرح بها، وتعافٍ موثق من الأعطال والتزامن. أي نتيجة محاكاة لا تحل محل اختبار جلسة أو تخزين فعلي.

قبل تنظيف البيئة، حفظ تقرير منقح ومقارنات النتائج. التنظيف في مسار finally حتى عند الفشل: إيقاف العامل والتطبيق والخدمات، إزالة الحاويات والأحجام وملفات البيانات والمفاتيح والجلسات الخاصة بالتشغيل فقط؛ لا أوامر حذف Docker عامة. إثبات توقف العمليات وعدم بقاء موارد التشغيل. تعذر التنظيف يُسجل كفشل مفتوح، لا نجاح.

**قبول مستقل لا يعني جاهزية الإنتاج:** عامل الإنتاج قليل الصلاحيات، مراقب التعليق، إعداد الجدولة/الاستضافة، مراجعة SQL الإنتاج والموافقة عليها ما زالت مرحلة منفصلة. غياب ملفات عميل تاريخية بلا metadata غير قابل للإثبات بهذه الخطة، واستثناء معاينة الدعوة أثناء الحجر يبقى موثقًا.

## تفاصيل التنفيذ المقترحة بعد الموافقة

الحفاظ على الملفات الحالية؛ إضافة حزمة تحت `integration/local-schema/acceptance/` فقط: دليل التشغيل، فحص العزل والمتطلبات، إعداد مستقل معتمد للنسخة التجريبية، تجهيز هويات رسمية/جلسات، بيانات تجريبية، سيناريوهات UI/RPC/Storage، سيناريوهات الأعطال والأقفال، تجميع الأدلة، والتنظيف. لا تعديل للـbaseline أو مسارات الترحيل المستضافة، ولا كتابة أسرار في المصدر.

## المطلوب قبل بدء الإعداد

الموافقة على الخطة، ثم تحديد جهاز موجود يدعم Docker أو مشغّل موجود معتمد، وإثبات عدم الإنفاق المدفوع إن استُخدم مشغّل خارجي، والموافقة على تسجيل الهويات الأربع رسميًا داخل البيئة المستقلة بعد تشغيلها. لا خدمات ولا حسابات ولا اتصال خارجي يُنشأ قبل هذه الموافقة.
