# المرحلة الأولى — تنفيذ محلي جزئي، 2026-11-02

## الحكم
**غير جاهزة للاعتماد أو التفعيل الإنتاجي.** التنفيذ التالي محلي؛ لا يتجاوز شروط المستخدم التي تمنع تغييرات الإنتاج قبل قبول مستقل ونسخة قابلة للاستعادة. لم تُطبق أي migration على Lovable Cloud، ولم تُغيّر بيانات أو إعدادات، ولم يُنشأ حساب أو خدمة، ولم يُنشر أو يُرفع إلى GitHub.

## ما نُفذ فعليًا
- طبقة مشتركة لـDataApi للتحقق من تعديل/حذف العملاء والطلبات والحجوزات والمهام بناءً على الإسناد الحالي؛ منشئ السجل ليس بديلًا عن المسؤول. هذه الطبقة ليست بديلًا عن RLS.
- أذونات مستقلة للتعديل والحذف، محددة بالمكتب ونوع السجل ومعرفه والموظف؛ الإسناد الجديد يبطل تفويض المسؤول السابق.
- واجهة منح/إلغاء أذونات العميل، وعطلت أدوات التعديل/الحذف لمن لا يملك الإذن. مسار التجربة يحفظ الأذونات محليًا، والمسار السحابي الجديد محجوب قبل Auth إلا عند تحقق البيئة المحلية المستقلة.
- منع الموظف من إعادة إسناد عمله عبر DataApi. لم تُعد إسنادات السجلات القديمة.
- حذف العميل في التجربة يستخدم مجموعة علاقات محددة، ويشمل تبعيات زملائه الحصرية ويترك العملاء الآخرين؛ العلاقات المتعارضة أو المسارات المشتركة توقف التنفيذ قبل الحذف.
- تصحيح هوية المنفذ في التعديلات التجريبية بدل نسبتها دائمًا للمدير.
- ملفان SQL إضافيان مستقلان يجهزان جدول الأذونات وسياسات القراءة المكتبية والتعديل/الحذف المحدد، تدقيق الدور والإسناد والإذن وطلب الحذف، استبقاء حارس آخر مدير، وقفل العميل بدل المكتب. **لم يطبقا على منصة حقيقية؛ جرى تركيبهما في PGlite فقط.**
- الملف الثاني يمنع الحذف المباشر لملفات documents ويقيّد الكتابات الجديدة، ويجهز منع تداخل حذف الوثيقة مع العميل، وتسلسل الجذر ثم المهمة وحماية المحاولة والمهلة الموجودة.

## تحقق فعلي للقراءة فقط
- `anon` و`authenticated` يملكان TRUNCATE على 14 من 15 جدولًا عامًا، وTRIGGER على جميع الجداول الـ15؛ لم تُجرّب هذه الامتيازات ولم تُغيّر.
- لم يُرجع فحص عضويات هذين الدورين عضويات موروثة. منح الإنشاء الافتراضية في public ما زالت واسعة لدى منشئي postgres وsupabase_admin؛ التحصين السابق المستقل يجهز تضييقها، لا يعني أنه مطبق.
- لا `deletion_jobs` ولا `work_record_permissions` في الخلفية المشتركة.
- لا HTTP schedule مسجل. المصدر يحتوي عاملًا محليًا فقط؛ لا دليل على عامل سحابي فعلي وآمن، ولا تكفي قائمة المواعيد الخالية لنفي أي عامل خارجي غير مرصود.
- 7 وثائق: جميعها تطابق عناصر في كتالوج Storage، واحدة بلا روابط عميل/طلب/حجز، وصفر تعارضات في روابط العميل/الطلب/الحجز المفحوصة. هذا لا يثبت محتوى الملفات أو تنزيلها أو استعادتها أو الحصرية الكاملة.

## ما تعذر أو لم يكتمل
1. لا بيئة مستقلة مثبتة بخدمات Auth وStorage وجلسات أربع هويات. PGlite ليست تلك البيئة؛ Docker/Podman غير متوفرين محليًا، ولم تُنشأ خدمات خارجية.
2. لا دليل على export قاعدة قابل للاستعادة مع نسخة ملفات وجرد متوافق واختبار استعادة. لا توجد أداة لقراءة مخزون النسخ اليومية؛ لا أؤكد تاريخ نسخة أو قابليتها للاستعادة. النسخ اليومية وتصدير Lovable Cloud لا يشملان ملفات Storage.
3. لذلك لم تُطبق سياسات الإنتاج ولم يُفعّل عامل سحابي أو جدولة أو صلاحيات جديدة.
4. لم تُختبر جلسات حقيقية، منع API/RPC/Storage المباشر، إزالة آخر مدير تحت التزامن، سباقات التفويض/الإسناد، حذف ملفات حقيقي وفشلها وإعادة المحاولة، إعادة التشغيل، أو الاستعادة.
5. ملفات SQL الجديدة **مسودة تنفيذ غير مفعلة، وليست حزمة إطلاق**: ما زال يلزم قبول تزامن متعدد الاتصالات، تثبيت أقفال العلاقات كلها، تطابق نطاقات التقارير ذات SECURITY DEFINER مع الحجر، شمول حصرية العلاقات للمهام/المشاركات وكل روابط الوثائق، ومنع تبديل روابط سجلات العمل باستغلال إذن تعديل سجل. تركيب SQL لا يثبت هذه القواعد.
6. واجهة التفويض الحالية للعملاء فقط؛ ربط واجهات أذونات بقية السجلات ووثائق/عمرة بالتفويض الكامل، وإثبات تطابقها مع سياسات Storage، غير مكتمل. لا ادعاء بأن موظف الإنتاج صار يقرأ كل المهام أو أن ثغرات الإنتاج اختفت.
7. إيصال إكمال الحذف المنزوع الهوية محفوظ وفق التصميم السابق؛ قبول سجل موثوق للفشل والإكمال مع محو تدقيق العميل نفسه يحتاج التحقق المستقل.
